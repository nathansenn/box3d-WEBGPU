# Box3D WebGPU: 100 integration improvements for game and app consumers

Audit date: 2026-09-23. This list covers integration, packaging, public API and developer experience for people who want to drop Box3D physics into a game or app. It complements, and does not repeat, the engine-internal backlog in [ENGINE_100X_ROADMAP.md](ENGINE_100X_ROADMAP.md) (status in [ENGINE_100X_STATUS.json](ENGINE_100X_STATUS.json)) and the solver list in [MATH_SPEED_100.md](MATH_SPEED_100.md). Where an item overlaps, it cites the engine item as `ENGINE_100X #n` and covers only the consumer-facing part.

The delivery vehicle is [`packages/box3d-kit`](../packages/box3d-kit) (npm name `box3d-webgpu-kit`). It wraps the prebuilt `public/box3d/box3d.{js,wasm}` and `src/engine/native-world.ts`: up to 16 isolated worlds, preset scenes, impulses, projectile bodies with generation-checked handles, batched ray/sphere/box casts and overlaps, destroyBody, clear, replayHash, and capacity reserve up to 65,536 bodies.

Status as of 2026-09-27: 38 items are delivered, 26 are partly delivered and 36 are proposals. Items marked **Partly delivered in box3d-kit 0.7.0** (triggers, a character controller, `onStep` dispatch and a shared gravity constant, all built on queries because the native events and shapes are missing), **Delivered in box3d-kit 0.6.0** (optional cable/water/frame modules, single-file build, CLI templates, capabilities, handle-cost measurement), **Delivered in box3d-kit 0.5.0** (shared-memory worker frames, room server, inspector overlay, leak recovery), **Delivered in box3d-kit 0.4.0** (Babylon.js adapter, changed-row uploads, examples, versioning policy, drift check, fuzzing, CSP verification, attribution), **Delivered in box3d-kit 0.3.0** (raw WebGPU writer, units/axes contract, multi-world scheduler, network snapshots, structural vector inputs, size budgets, SSR-safe imports), **Delivered in box3d-kit 0.2.0** (render interpolation, query helpers, worker hosting, record/replay, stats, capacity reservation, pause handling, error-code union) or **Delivered in box3d-kit 0.1.0** are in the kit. Items marked **Partly delivered** say what remains. The 0.1.0 deliveries were: the loader decoupled from Vite, the fixed-step accumulator, body pose readback, the three.js instanced adapter, the npm tarball with WASM and licenses, and the tarball smoke test. Every unmarked item is a proposal. No item claims a measured speedup; performance items state what to measure.

Core physics API completeness is listed first because it gates the rest; the remaining categories follow.

Machine-readable copy: [INTEGRATION_100.csv](INTEGRATION_100.csv). Priorities: P0 blocks basic game use; P1 is needed for a solid 1.0; P2 widens reach. Effort: S ≈ days, M ≈ 1–2 weeks, L ≈ several weeks.

## The main gap

The C bridge (`wasm/box3d_web.c`) has no exported general body creation. `b3w_ctx_add_box_ex` is static, and bodies come only from preset scenes, demos, rain and projectile cubes. Only box hulls exist: no sphere, capsule, mesh or heightfield shapes, no joints, no exported pose or velocity get/set, no gravity setter, no contact or sensor events, and no collision filter on bodies. Item #1 is therefore P0 and gates most of the list. Rebuilding the WASM needs the upstream source, which is not vendored (`scripts/fetch-box3d.sh` clones `erincatto/box3d` v0.1.0), and Emscripten 4.0.23 (`scripts/build-wasm.sh`).

## Top 10 to do first (dependency order)

1. **#1 General body creation.** Without general body creation a game can only spawn presets, rain and projectile cubes; nearly every API, adapter and example item depends on it.
2. **#3 World definition and gravity.** Gravity and the forced ground box must be controllable before any consumer scene is meaningful.
3. **#2 Body state get/set.** Games need to read and set velocity and teleport bodies; batched access keeps boundary crossings low.
4. **#14 Remove ScenePreset from the core.** Removing ScenePreset from the core type graph lets the kit ship without demo content.
5. **#15 Official Node target.** box3d-kit already loads in Node by passing the bytes; a Node-targeted build extends that to Deno, Bun and other runtimes.
6. **#5 Per-body materials and collision filtering.** Games need friction, restitution, category/mask bits and sensor flags on bodies before queries and events can be targeted.
7. **#24 Stable handle-to-instance mapping.** Partly delivered in box3d-kit 0.2.0: user data by handle and row-move detection. Native stable instance slots remain.
8. **#4 Non-box shapes.** Sphere, capsule, mesh and heightfield shapes are the minimum for most games.
9. **#6 Contact and sensor events.** Contact and sensor events unlock triggers, damage, audio and the controller. box3d-kit 0.7.0 approximates triggers and the controller with queries (#25–#27); native events remain.
10. **#41 Worker-hosted worlds.** Delivered in box3d-kit 0.2.0 (`box3d-webgpu-kit/worker`). Next is the SharedArrayBuffer pose ring (#42).
